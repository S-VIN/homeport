# Архитектура rproxy

Один процесс владеет ядром, плагинами и mihomo. Окно и каждая вкладка браузера рисуют один и тот же egui-интерфейс: код UI выполняется на хосте, браузер получает готовые фигуры и отправляет ввод. Поэтому в коде плагинов нет клиента, сервера и протокола. Как писать плагины — [PLUGINS.md](PLUGINS.md); соглашения интерфейса — [DESIGN.md](DESIGN.md).

## Слои

```text
src/            приложение: CLI, окно eframe, трей, веб-сервер, каталог плагинов
plugins/*       вся функциональность (servers, subscriptions, форматы, routing, …)
crates/kernel   плагины, State/Op/Event/Slot, писатель транзакций, SQLite, задачи,
                mihomo как сервис, оболочка окна и её зоны, сессии UI, Host
crates/kit      дизайн-система egui без домена: токены, палитра, шрифты, иконки, виджеты
crates/mihomo   типизированный конфиг (Fragment → Config → JSON), процесс и контроллер
crates/remote   удалённый egui: хост-стример и wasm-клиент («экран» без кода приложения)
crates/derive   #[derive(Table)] для SQLite
```

Ядро и kit не зависят от плагинов. Плагин зависит от `rproxy-kernel` и от крейтов плагинов, чьи типы использует (`requires` в манифесте).

## Ядро

- **Host** блокирует каталог данных, открывает `rproxy-plugins.sqlite3` и держит текущий `Kernel`. Смена набора плагинов перезапускает ядро в том же процессе; окна и вкладки браузера продолжают работать и рисуют новое ядро.
- **Kernel::start**: сохранённые переключатели плагинов → разрешение зависимостей и Exclusive-категорий → `setup` каждого плагина в порядке зависимостей → миграции → загрузка состояния → запуск mihomo с составленным конфигом → расписания → событие `Started`.
- **Запись** (`cx.write`) выполняется одним писателем:
  1. синхронное замыкание над свежим снимком (copy-on-write затронутых ячеек, проверка владельца);
  2. каскады удаления;
  3. новый снимок → компоновка фрагментов всех плагинов → применение в mihomo (только выбор группы или полный конфиг);
  4. коммит SQLite; при ошибке ядро возвращает прежний конфиг mihomo;
  5. публикация снимка, перерисовка сессий, события, перепланирование расписаний.
  Читатели берут снимок без блокировок.
- **Op** — действие с цепочкой обработчиков (ранг, вес заявки, порядок зависимостей). Op с `JobSpec` запускается фоновой задачей: прогресс, отмена, объединение или очередь по ключу.
- **mihomo** работает с домашним каталогом `<data>/core`: там кэш гео-списков (`rules/*.mrs`) и обновлённое ядро (`bin/mihomo`, побеждает комплектное; см. `updates.rs`). Служебный SOCKS-вход `routed` идёт по обычным правилам — через него ядро и плагины скачивают то, что напрямую недоступно. Конфигурация (`configuration.rs`) экспортируется явным действием пользователя в переносимый SQLite-файл; импорт проверяет схему и значения до подтверждения. При применении временный снимок позволяет откатить неудачный запуск; постоянные бэкапы и их расписание отсутствуют. Native frontend открывает системный файловый диалог, web frontend передаёт файл по тому же защищённому WebSocket.
- **mihomo**: ядро под внутренним `rproxy --core-supervisor`: owner pipe закрывается при выходе или аварии приложения; supervisor завершает и reap-ит дочернее ядро. Windows Job создаётся до spawn; Linux PDEATHSIG служит дополнительной защитой, но owner pipe работает и с file capabilities. Остановка Host сериализована с restart/import и окончательна; контроллер на Unix-сокете (Linux/macOS) или loopback TCP со случайным bearer-секретом (Windows), изолированные «полосы» проверок: N служебных SOCKS-входов `checks-i`, каждый со своей группой `test-i` (`cx.core().lease(target)` берёт свободную полосу, до `mihomo::CHECK_LANES` одновременно; имена `test*`/`checks*` зарезервированы). Задержка и HTTP-тесты идут через delay API mihomo (`cx.core().probe(proxy, url, timeout, expected)`) без аренды и параллельно. Слушатели, которые не смогли занять порт при старте, отмечаются ошибкой, остальные работают; новый слушатель, который не стартует, отклоняет правку.

## Удалённый egui

На каждую вкладку браузера хост создаёт `egui::Context` и сессию UI. Кадр: `ctx.run(raw_input)` → фигуры переводятся в сериализуемый вид, раскладки текста кэшируются по хешу, список фигур передаётся дельтой к прошлому кадру, всё сжимается deflate. Клиент на wasm тесселирует фигуры и рисует их, атлас шрифтов хоста — его текстура; обратно идёт `RawInput`. Протокол не зависит от приложения. Первый кадр UI около 7 КБ, неизменный кадр 16 байт. Десктопное окно — та же сессия без сети. Клиент пересылает и «тихие» изменения ввода: смену системной темы (тема System переключается без перезагрузки) и позицию указателя перед событием колеса, чтобы прокручивалась область под ним; программная прокрутка страницы превращается в событие колеса (`web/index.html`).

## Проверки

```sh
cargo test --workspace
cargo clippy --workspace --all-targets
```

`crates/kernel/tests/kernel.rs` — механика ядра на тестовых плагинах. `tests/e2e.rs` — настоящий mihomo: форматы, загрузка, выбор, маршруты, слушатели с авторизацией, проверки через изолированный маршрут, автовыбор, перезапуск. `crates/remote/tests` — кадры оболочки по проводу, в том числе декодирование под wasm32 (`wasm-bindgen-test-runner`).
