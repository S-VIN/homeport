# rproxy на VDS

Нужен Linux VDS с Docker Engine, Docker Compose и двумя DNS-именами под одним
родительским доменом: например `panel.example.com` и `auth.example.com`.
A-записи обоих имён должны указывать на IP сервера. AAAA добавляйте только при
работающем IPv6 и соответствующем `CADDY_BIND`. Для этой схемы нужны домены.

## Установка

На сервере достаточно `compose.yaml`, `Caddyfile` и `.env`. Сборка на VDS не нужна:
Compose скачивает `ghcr.io/s-vin/rproxy:latest`, официальный Tinyauth и Caddy.

```sh
cp .env.example .env
chmod 600 .env
```

Заполните в `.env` домены, `DATA_DIR`, `TINYAUTH_USERNAME` и `TINYAUTH_PASSWORD`.
Пароль указывается обычным текстом в одинарных кавычках: они сохраняют `$` и
пробелы; одинарную кавычку внутри пароля экранируйте как `\'`. Tinyauth сам
генерирует bcrypt при старте. Отдельная команда генерации хеша не нужна.
Не публикуйте `.env`: файл содержит пароль.

```sh
docker compose up -d
```

Откройте `https://panel.example.com:8443` и войдите с указанными данными.
Caddy получает и продлевает публичные сертификаты автоматически; первый выпуск
может занять минуту. Диагностика: `docker compose ps` и `docker compose logs --tail=100`.

## Настройки

Все параметры установки находятся в [.env.example](.env.example).
Править Compose и Caddyfile для смены доменов, портов или каталога данных не нужно.

| Переменная | Назначение |
| --- | --- |
| `RPROXY_PANEL_DOMAIN`, `RPROXY_AUTH_DOMAIN` | Два разных домена панели и входа, без схемы и порта |
| `DATA_DIR` | Абсолютный путь к общей папке данных на VDS |
| `TINYAUTH_USERNAME`, `TINYAUTH_PASSWORD` | Логин и пароль администратора |
| `HTTPS_PORT`, `HTTP_PORT` | Публичные порты Caddy; по умолчанию 8443 и 80 |
| `CADDY_BIND` | Адрес слушателя Caddy; по умолчанию все IPv4-адреса |
| `RPROXY_UI_PORT`, `TINYAUTH_PORT` | Внутренние порты на 127.0.0.1; по умолчанию 20800 и 20801 |
| `ACME_EMAIL` | Необязательный контакт для сертификатов |
| `WS_MAX_DURATION` | Максимальная длительность WebSocket до повторной проверки входа; по умолчанию 1h |
| `RPROXY_IMAGE`, `TINYAUTH_IMAGE`, `CADDY_IMAGE` | Образы, версии или digest |
| `TZ`, `LOG_MAX_SIZE`, `LOG_MAX_FILES` | Часовой пояс и ограничение Docker-логов |

Все порты должны быть свободны и различаться. В firewall откройте SSH, TCP 80,
выбранный HTTPS-порт и нужные прокси-порты. Для ACME HTTP-01 всегда нужен доступ
снаружи по TCP 80: при другом `HTTP_PORT` настройте перенаправление с публичного 80.
Внутренние порты панели и Tinyauth открывать не нужно.

HTTPS по умолчанию использует 8443, оставляя TCP 443 для VLESS/REALITY.
Можно выбрать `HTTPS_PORT=443`, если этот порт не нужен другому слушателю.
Встроенный сайт VLESS может получать сертификат через TLS-ALPN на 443;
его слушатель HTTP 80 включать не нужно — порт занят Caddy.

После изменения `.env` выполните `docker compose up -d`. Это также применяет
новый логин или пароль. Все вошедшие пользователи имеют полное управление rproxy.

## Сеть и авторизация

Все три контейнера используют сеть хоста. rproxy может открывать любые свободные
TCP/UDP-порты без добавления `ports` в Compose. Адреса и порты прокси-входов
настраиваются в интерфейсе и хранятся в базе приложения.

Панель rproxy и Tinyauth слушают только 127.0.0.1. Caddy проверяет авторизацию для
всех URL панели, включая JS, WASM и `/ws`. WebSocket дополнительно проверяет
Origin. Выход из Tinyauth блокирует новые подключения; уже открытое подключение
завершается не позднее `WS_MAX_DURATION`, затем требует повторной авторизации.

Процессы контейнеров работают от root, чтобы Docker мог сам создавать каталоги
данных без подготовки UID и владельцев. Файловые системы контейнеров доступны
только для чтения, `/tmp` временный, включён `no-new-privileges`. Все capabilities
удалены; только rproxy и Caddy получают `NET_BIND_SERVICE` для портов ниже 1024.
Доступа к Docker socket и режима privileged нет.

Tinyauth защищает управление. Для внешнего HTTP/SOCKS-входа задайте собственные
логин/пароль во вкладке Inbounds. По умолчанию такой вход слушает `127.0.0.1:20808`.

## Данные и обновление

Docker создаёт подкаталоги внутри `DATA_DIR`:

```text
/srv/rproxy/          # DATA_DIR
  rproxy/            # профиль и база приложения
  tinyauth/          # база авторизации
  caddy/
    data/            # сертификаты и ключи
    config/          # состояние Caddy
```

Это обычные папки хоста. Они сохраняются при пересоздании контейнеров и
`docker compose down -v`. Для согласованной резервной копии остановите стек
и сохраните весь `DATA_DIR` вместе с `.env`. Данные из прежних именованных томов
автоматически не переносятся.

```sh
docker compose pull
docker compose up -d
```

Для фиксированной версии укажите версионный тег или digest в `RPROXY_IMAGE`.

## Публикация образа

**Actions → Docker image → Run workflow** публикует
`ghcr.io/s-vin/rproxy:latest` для `linux/amd64` и `linux/arm64`.
Тег `v0.2.0` публикует версионный тег `0.2.0`. Каждый образ содержит свой
проверенный бинарник mihomo из Git; скачивания mihomo при сборке нет.
Архитектуры собираются параллельно на нативных x64/ARM64 runners с отдельными
кэшами слоёв. После успеха обеих сборок публикуется общий multi-platform тег.
Workflow не запускает тесты и не собирает дополнительный тестовый образ.

Для скачивания образа без входа сделайте пакет публичным в GitHub Packages.
Для приватного пакета выполните на VDS `docker login ghcr.io` с токеном,
имеющим `read:packages`. Workflow публикует образ через `GITHUB_TOKEN`.

## Проверка разработки

Из корня проекта:

```sh
docker build -f docker/Dockerfile -t rproxy:deployment-test .
python3 -m venv /tmp/rproxy-tests
/tmp/rproxy-tests/bin/pip install aiohttp
/tmp/rproxy-tests/bin/python scripts/test-docker-auth.py
```

Тест запускает настоящий Compose с временными данными, произвольными
loopback-портами и локальным CA. Проверяет вход, неверный пароль, защиту
ресурсов и WebSocket, Origin, выход, смену пароля, сохранность данных и
сертификатов после пересоздания контейнеров. Затем удаляет тестовый стек.

Конфигурация использует официальные интерфейсы
[Tinyauth/Caddy](https://tinyauth.app/docs/community/caddy/) и
[Tinyauth v5](https://tinyauth.app/docs/reference/configuration/).
